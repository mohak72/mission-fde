# Story 2.3: Read-Only kubectl Evidence Grounding

## Status

Approved

## Story

As an on-call engineer,
I want the diagnosis to cite live cluster state, not just the runbook text,
so that I can trust the diagnosis reflects what's actually happening right now, not a generic guess.

### Acceptance Criteria

1: The investigate node calls read-only `kubectl get`/`describe` against the target cluster (local `kind` for dev/test) for resources relevant to the alert.
2: The tool is strictly read-only — no code path from this node to any write/mutating kubectl verb (NFR5).
3: The final proposal cites specific live evidence (e.g., "pod X in CrashLoopBackOff, restart count N") alongside the runbook citation.
4: If the cluster/tool call fails or times out, the system still returns a diagnosis, clearly flagged as "not grounded in live state," rather than failing the whole pipeline.

## Known Gaps in Architecture Docs

1. **No `ClusterEvidence` shape is defined anywhere.** Recommended default given above in Task 1 (pydantic model: `resource_kind`, `resource_name`, `namespace`, `status_summary`, `raw`).
2. **No doc specifies which alert labels identify the target Kubernetes resource.** Recommended default: `namespace` + (`pod`, else `deployment`) from the same `alert.payload["labels"]` dict `classify.py` already reads; if neither is present, skip the API call entirely rather than erroring.
3. **`components.md` says `get_evidence` "never raises"; `error-handling-strategy.md` says the *node* catches `ClusterEvidenceError`.** These aren't actually contradictory once sequenced correctly: `evidence.py` raises `ClusterEvidenceError` (so the Critical Rule about raw SDK exceptions never leaving their owning module holds), and `investigate.py` catches it (so error-handling-strategy's "node handles its own failure gracefully in-graph" framing holds). The net effect — the pipeline never sees a raw failure — is exactly what `components.md` describes, just achieved one layer up. This story implements it that way; flagging so Dev doesn't try to satisfy both docs literally by having `evidence.py` itself swallow the error, which would violate the error-translation-boundary rule.
4. **No timeout value is specified for kubectl calls** (Test Strategy explicitly says no latency SLA exists for M1). Recommended default: an explicit ~10s `_request_timeout` on every Kubernetes API call, chosen so AC4's degradation path triggers before a hung cluster call stalls the whole run — same fail-fast spirit as the Gateway's retry/timeout handling, not a value derived from any stated requirement.
5. **No `kind` cluster exists yet** in `docker-compose.yaml`, in CI, or (as far as can be verified at drafting time) in whatever sandbox executes this story's implementation. This is new infrastructure Task 4 must add. If the implementing environment genuinely cannot run a local `kind` cluster, the integration test must still be written correctly for CI and the gap stated plainly — not silently skipped.
6. **Whether `propose.py`'s "reused unchanged" instruction still applies.** It does not, for this story: AC3 requires the LLM's own output to incorporate live evidence, so `propose_diagnosis` needs the new `live_evidence` parameter described in Task 3. The *default* behavior (parameter omitted/`None`) must stay byte-identical to today, which is what keeps Story 2.2's regression fixture valid — but the function itself is legitimately in scope for a real, additive change here.
