## Story

**As an** on-call engineer,
**I want** the system to produce a cause + next-steps summary from the alert and its matched runbook,
**so that** I get an initial diagnosis without manually reading the runbook myself.

## Acceptance Criteria

1. Given an alert + its retrieved runbook, the system calls the LLM gateway (never the model provider directly, per NFR1) and returns a structured diagnosis: probable cause + next-step action.
2. The diagnosis explicitly references which runbook section it drew from.
3. If retrieval returns no runbook above a confidence threshold, the system returns an explicit "no matching runbook" result rather than a hallucinated diagnosis.
4. Unit tests cover: happy path, low-confidence-retrieval fallback, gateway-call-failure handling (retry/error surfaced, not swallowed).

## Concepts You Need

_(Read this before starting — these are the ideas this story actually exercises, not generic background.)_

- **AWS Labs tie-in (G1):** this is the first story in the roadmap that touches AWS Bedrock — hands-on Bedrock Converse API usage mapped directly to the AIP-C01 cert lab G1. Everything else in S1–S12 reuses this same Gateway seam. [Source: architecture/tech-stack.md]
- **Why the confidence threshold belongs in the Retrieval Service, not the LLM call.** AC3 is about preventing garbage-in at the source: if nothing in the corpus is actually close enough to the alert, the right move is to never hand the LLM anything to hallucinate from, not to ask the LLM to "say if you're not sure." This is why Task 2 modifies `retrieve_runbook` itself (adding the threshold Story 1.3 deliberately deferred — see that story's "Concepts You Need") rather than adding a confidence check downstream in the prompt.
- **Why a raw `botocore` exception must never leak past the Gateway.** Same shape as Story 1.3's NFR8 rule for `chromadb` — NFR1's whole point is that swapping Bedrock → OCI Gen AI at Story 5.1 is a change inside `platform/gateway/`, not a hunt-and-replace across every caller that might have caught a Bedrock-specific exception type.
- **Why this story builds retry + timeout, but not the circuit breaker.** Error Handling Strategy describes the circuit breaker's purpose as protecting "the rate-limit budget (NFR1)" — but the rate limiter itself (the thing with a budget to protect) is explicitly Story 3.2's scope. Building a circuit breaker to protect a budget that doesn't exist yet would be building ahead of its own dependency; this story implements retry (exponential backoff, max 3 attempts, transient errors only) and the 30s timeout, and explicitly defers the circuit breaker, flagged as a deliberate sequencing call rather than an oversight.
- **Mocking the Gateway in tests isn't a workaround for missing credentials — it's the architecture's actual design.** Test Strategy's asymmetric-mocking choice (real Postgres/Chroma, mocked Gateway) would be true even with AWS credentials in hand; this story's tests would look identical either way.
- **This story does not persist anything.** `DiagnosisProposal.pipeline_run_id` is a `NOT NULL` foreign key to `pipeline_runs` — and `PipelineRun`/the graph don't exist until Story 2.2. This story's output is a return value from a function call, not a database row; persistence is explicitly Story 2.2's job once there's a `PipelineRun` for the proposal to hang off of.
