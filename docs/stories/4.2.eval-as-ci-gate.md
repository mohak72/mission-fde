# Story 4.2: Eval as CI Gate

## Status

Draft

## Story

As a developer,
I want the Story 3.4 eval harness to run automatically in CI and fail the build on regression,
so that a diagnosis-quality regression is caught before merge, not after deploy.

### Acceptance Criteria

1: The eval harness (Story 3.4) runs as a step in the GitHub Actions CI pipeline (building on Story 1.1's CI).
2: CI fails if retrieval hit-rate or judge score drops below a committed baseline threshold.
3: The baseline threshold is stored in the repo (not hardcoded in the workflow file), so updating it is a reviewable diff.
4: A CI badge in the README reflects current pipeline status.

## Batch-Draft Assumptions (revalidate before development)

This story was drafted on 2026-11-16 in a batch with all of Epics 3 and 4, **before any Epic 3 story was implemented**. The thing this story gates on, the eval harness, does not exist: `apps/incident-copilot/src/incident_copilot/eval/` is an empty package on `main` at commit `0652292`. Everything below about the harness is taken from the PRD and architecture docs, not from code. Before development, re-read Story 3.4's Dev Agent Record and correct this story wherever it differs.

1. **The harness is runnable as one command** (Story 3.4 AC4). Components names it `copilot eval`; the real command name, arguments, and exit-code behaviour are unknown until 3.4 ships.
2. **It writes a persisted report** in JSON and/or markdown (Story 3.4 AC4). Assumed: the JSON contains at least `retrieval_hit_rate` and `judge_score` as numbers, matching the `EvalRun` model. The actual file path, field names, and score scale (0–1, 1–5, percent) are unknown.
3. **It runs the 20 incidents through the real `run_pipeline`** (Components: "the same pipeline, not a parallel implementation") and so needs Postgres, the Chroma runbook index, and, since Story 2.3, a reachable Kubernetes API or a graceful degradation when there is none.
4. **Retrieval hit-rate is computed without any LLM call** (it compares the retrieved runbook ID with the expected one), while the judge score needs real LLM calls for both the diagnosis and the judge. This split is the basis of Known Gap #1's recommendation; confirm 3.4 actually lets the two be run separately.
5. **The harness does not itself enforce a threshold.** Story 3.4 AC5 says a hit-rate under 80% is "flagged as a known gap, not hidden", which reads as reporting, not failing. Assumed: the pass/fail decision is new work in this story.
6. **Stories 3.1 and 3.2 will have added a response cache and rate limiter to the gateway.** A cache can make repeated eval runs cheaper; a rate limiter can slow or reject a 40-call eval burst. Their defaults are unknown.
7. **Story 3.4 will have produced a first real set of numbers.** A baseline threshold has to come from measured results; if 3.4 only ever ran with a mocked gateway, there is no judge-score baseline to commit.

## Concepts You Need

- **This is the first CI job in this project that would call a real LLM.** Every tier so far mocks the gateway on purpose: "real LLM calls are reserved for the Eval Harness tier, not integration tests, to keep this tier fast, deterministic, and free to run on every CI build." Putting the eval in CI gives up all three of those properties for one job. [Source: architecture/test-strategy-and-standards.md#integration-tests]
- **A judge score is not deterministic.** The same code can score differently on two runs. A gate with a tight threshold on a noisy number will fail builds that changed nothing, and people stop trusting a gate that does that. How the threshold absorbs noise is the central design question of this story (Known Gap #3).
- **CI currently has no secrets at all.** `.github/workflows/ci.yaml` uses none; the Postgres password in it is a throwaway service-container value. A real-LLM eval needs AWS credentials in GitHub Actions, and GitHub does not expose secrets to workflows triggered by pull requests from forks. [Source: .github/workflows/ci.yaml]
- **The README badge already exists.** `README.md` line 3 is a badge for `ci.yaml`, added in Story 1.1. AC4 is met as long as the eval gate lives in that same workflow; if it moves to a separate workflow file, the badge no longer reflects it. [Source: README.md]
- **NFR4 says the eval runs "on every change".** Taken literally, that is a billable, multi-minute, non-deterministic job on every push and every PR update. Known Gap #1 proposes how to honour it without that cost; it is a user decision. [Source: docs/prd/requirements.md]

## Tasks / Subtasks

- [ ] **Task 1: Committed baseline file (AC: 3)**
  - [ ] Add a baseline file in the repo, outside `.github/` (recommended: `apps/incident-copilot/src/incident_copilot/eval/baseline.json` or `.yaml`), holding the minimum retrieval hit-rate and minimum judge score, plus the date, model ID, and eval-set version they were measured with.
  - [ ] Values come from Story 3.4's measured results and Known Gap #3's margin rule, not from a guess. FR8's 80% hit-rate target is the floor for retrieval if measured results support it; if 3.4 measured below 80%, the baseline records the measured reality and the gap stays flagged per Story 3.4 AC5.
  - [ ] The workflow file must contain no threshold numbers.

- [ ] **Task 2: Gate check (AC: 2)**
  - [ ] Add a small, separately testable function and command that reads the eval report and the baseline file and exits non-zero if either metric is below its threshold, printing both numbers and both thresholds either way.
  - [ ] It must fail, not pass, when the report is missing, unparseable, or lacks a metric the baseline requires. An eval that crashed must not read as a pass.
  - [ ] If the judge score was deliberately not computed in this run (Known Gap #1), the output must say "judge score: not evaluated in this run", never show it as passed.
  - [ ] Unit tests: both above threshold; hit-rate below; judge below; exactly equal to threshold (decide and document: equal passes); missing report; malformed report; judge not evaluated.

- [ ] **Task 3: CI job (AC: 1, 2)**
  - [ ] Add an `eval-gate` job to `.github/workflows/ci.yaml` as its own job, consistent with "separate CI jobs for lint → unit → integration → eval-gate ... so a failure is immediately attributable to a tier." [Source: architecture/test-strategy-and-standards.md#continuous-testing]
  - [ ] Provide what the harness needs: the Postgres service container and `alembic upgrade head`, the runbook index, the cached Chroma embedding model (reuse the existing `actions/cache` step), and a kind cluster or a confirmed graceful degradation without one. Copy the working pattern from the existing `integration-test` job.
  - [ ] Run the harness, then the gate check. Upload the eval report as a workflow artifact on success and on failure (`if: always()`), so a failed gate can be diagnosed from the PR. (Story 3.4 AC4: "can be committed or attached to a PR".)
  - [ ] Implement the trigger and scope decided under Known Gap #1.
  - [ ] Set a job timeout and a `concurrency` group so superseded runs on the same PR are cancelled and not billed.

- [ ] **Task 4: Credentials in CI (AC: 1)**
  - [ ] Only if the user approves a real-LLM tier (Known Gap #2). Recommended mechanism: GitHub OIDC to an AWS IAM role (`aws-actions/configure-aws-credentials`) scoped to `bedrock:InvokeModel` on the specific model, so no long-lived AWS key is stored in GitHub. Fallback: repository secrets.
  - [ ] The workflow must behave sensibly where secrets are unavailable (fork PRs, Dependabot PRs): skip the real-LLM part with a visible notice. Decide whether a skipped judge tier blocks merge.
  - [ ] No credential may be echoed, written to the report artifact, or logged. [Source: architecture/coding-standards.md#critical-rules]

- [ ] **Task 5: Prove the gate can fail (AC: 2)**
  - [ ] On a throwaway branch, deliberately degrade retrieval (for example, raise the confidence threshold so most incidents miss) and confirm the `eval-gate` job goes red and the artifact shows why. Record the run URL in Completion Notes. Do not merge that branch.
  - [ ] Confirm that raising the baseline in a PR shows up as a normal reviewable diff (AC3).

- [ ] **Task 6: Badge and docs (AC: 4)**
  - [ ] Confirm the existing README badge covers the workflow containing the gate. If the real-LLM tier lives in a separate workflow file, add a second badge for it.
  - [ ] Add a short README section: how to run the eval locally, where the baseline lives, how to update it, and what each CI trigger runs.

- [ ] **Task 7: Make the gate required (AC: 2)**
  - [ ] A failing job only blocks a merge if branch protection on `main` requires it. This is a repository setting, not a file in the repo. Check whether `main` has required status checks; if not, tell the user, since changing repository settings is theirs to do. Note that PRs #4 and #5 were merged by the user directly, and a gate that is not required would not have stopped either.

- [ ] **Task 8: Full validation**
  - [ ] `ruff check .`, `bandit -r src`, `pytest tests/unit`, `pytest tests/integration`, `pip-audit`; validate the workflow YAML; confirm all existing CI jobs still pass.
  - [ ] Execute `.bmad-core/checklists/story-dod-checklist.md` before setting Status.

## Known Gaps in Architecture Docs

1. **What "runs on every change" means once the eval costs money and takes minutes.** No doc resolves NFR4 against Test Strategy's "free to run on every CI build" principle. Recommended default, two tiers in one workflow:
   - **Tier A, every PR and push, no credentials, no cost:** run the eval's retrieval half only and gate on retrieval hit-rate. It needs Postgres and Chroma, no LLM.
   - **Tier B, real LLM (diagnosis + judge), gate on judge score:** run on pushes to `main`, on a nightly schedule, and on demand (`workflow_dispatch` or a PR label), not on every PR commit.
   This meets AC2 for both metrics but checks the judge score after merge unless the label is used. If the user wants the literal reading (both metrics block every PR), every PR commit makes roughly 40 real LLM calls and fork PRs cannot run it. **User decision.**
2. **Real Bedrock access for CI does not exist.** Needed before Tier B can run at all: an AWS account with Bedrock model access for the chosen model, an IAM role or key for GitHub Actions, and acceptance of the spend. Recommended: before approving, have Dev compute an estimated cost per eval run from the measured token counts in Story 3.4's report and the current Bedrock price for the model, and set an AWS budget alarm. Do not start Task 4 without the user's go-ahead. **User decision / prerequisite.**
3. **How to set a threshold on a noisy score.** AC2 says "drops below a committed baseline threshold" and nothing more. Recommended default: run the full eval at least 5 times on unchanged code, record the spread, and set the judge threshold below the lowest observed run by a margin (for example, lowest minus one further standard deviation), documenting the runs next to the baseline. Request temperature 0 for the judge call if the gateway and model allow it. For retrieval (deterministic given a fixed index and embedding model), the threshold can equal the measured hit-rate with no margin. Whether a first failure triggers one automatic re-run before failing the build is a **user decision**: a retry reduces false alarms and also lets a real borderline regression through about half the time.
4. **Which judge model and whether it is pinned.** If the judge model or its prompt changes, old baselines are not comparable. Recommended: record judge model ID and judge-prompt version in both the report and the baseline, and have the gate check refuse to compare when they differ, with a message telling the developer to re-baseline.
5. **Whether the gateway's cache (Story 3.1) is on during the eval.** With the cache on, a repeated identical prompt returns the cached answer, which hides run-to-run variation within one process. Between CI jobs the in-memory cache is empty, so each job pays full price. Recommended: leave it at its default and state which in the report.
6. **Kubernetes in the eval job.** Story 3.4's synthetic incidents reference pods that do not exist in a fresh kind cluster, so the investigate node will degrade (`grounded_in_live_state=False`) for all of them, or skip the API call when labels are absent. Recommended: do not provision kind in `eval-gate`; confirm the pipeline degrades cleanly with no cluster reachable (it should, per Story 2.3 AC4 and QA REL-004) and note that the eval measures runbook-only diagnoses.
7. **Branch protection is outside the repo.** See Task 7.
