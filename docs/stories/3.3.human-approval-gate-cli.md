# Story 3.3: Human Approval Gate (CLI)

## Status

Draft

## Story

As an on-call engineer,
I want to see the proposed diagnosis and action and explicitly approve or reject it,
so that no action is ever taken without my sign-off.

### Acceptance Criteria

1: After a proposal is generated, a CLI command displays the diagnosis, evidence, and proposed action, and prompts for approve/reject.
2: An approval is logged with actor + timestamp and marks the proposal "approved — would execute" (no real executor exists yet for MVP).
3: A rejection is logged with actor + timestamp and the run ends as a no-op — nothing is executed.
4: The human-approval stub from Story 2.2 is replaced by this real implementation.
5: This fulfills FR6/FR7 — the literal "demo moment" from the RFC.

## Concepts You Need

- **The stub you are replacing is three lines.** `graph/nodes/approve.py` returns `{"approval_status": "pending"}`, held only in in-memory graph state. No `approval_decisions` table, no `ApprovalDecision` model, no repository, and `approval/` contains only an empty `__init__.py`. [Verified: `graph/nodes/approve.py`, `persistence/models.py`, listing of `approval/`]
- **Approval is asynchronous and out-of-process; the graph run is not.** `run_pipeline` executes all five nodes in one call and returns. A human approves minutes later, from a different process (a terminal). So the real gate cannot be "a node that blocks waiting for input". The durable hand-off point is the persisted `DiagnosisProposal` row: the graph produces it, the CLI decides on it. See Known Gap #1.
- **"Approved — would execute" is the whole outcome.** There is no executor and there must not be one (NFR5). Approval writes a row and a log line. A reviewer should be able to grep the codebase and find that the approve path calls nothing that could mutate a cluster. [Source: architecture/coding-standards.md#critical-rules — "No action-executor exists. Don't add one 'just to make the demo feel real.'"]
- **A proposal's state is derived, not stored.** `diagnosis_proposals` has no status column. Pending = no `ApprovalDecision` row; decided = one exists. The unique index on `approval_decisions.proposal_id` is what makes "decide once" a database guarantee rather than an application check. [Source: architecture/database-schema.md]
- **`grounded_in_live_state` exists for this screen.** Data Models says it is "surfaced to the approver so they know what they're approving". A proposal whose kubectl evidence degraded (Story 2.3 AC4) must look visibly different at the approval prompt.
- **Not every run has a proposal.** A no-match run (`DiagnosisResult.matched=False`) and a failed run complete without creating a `DiagnosisProposal`. There is nothing to approve for those, and the CLI must say so plainly rather than erroring.

## Dev Notes

### Previous Story Insights

- Story 2.2 created `DiagnosisProposal` + `DiagnosisProposalRepository.create()` only — there is no read method on that repository yet. Task 1 adds the first ones.
- Story 2.2 deliberately used `pipeline_runs.status='completed'` to mean "the run finished", independent of whether a human has acted, precisely so this story would not need a new run status. Do not add `pending_approval` to the CHECK constraint.
- Story 2.3 populated `live_evidence` with a `ClusterEvidence.model_dump()` shape: `resource_kind`, `resource_name`, `namespace`, `status_summary`, `raw`. Display `status_summary` as the headline — but treat every key as optional when rendering (a malformed/partial dict must not crash the approval screen; that failure shape is exactly what Quinn probed for in 2.3).
- Story 2.3's AST-based static guard is the template for Task 5's guard — note the lesson recorded there: a naive text scan false-positives on the module's own docstring.

- "One `DiagnosisProposal` → one `ApprovalDecision` (once decided; absent while pending)". [Source: architecture/data-models.md#approvaldecision]

## Known Gaps in Architecture Docs

1. **How does a synchronous graph "await" a human?** Core Workflows draws `GRAPH->>APPR: await approval` as if the run pauses. LangGraph can do that with `interrupt()` plus a persistent checkpointer, but that means a new persistence component and resumable runs — which Error Handling Strategy rules out for M1 ("a failed run is terminal", no run resumption). Recommended default: the run completes with a persisted, pending proposal; the CLI decides on it out-of-band; the `approve` node is the documented hand-off marker. Record LangGraph interrupt/resume as the known upgrade path, not as something half-built.
2. **Actor identity.** Data Models says "CLI user identity for MVP" with no mechanism. Recommended default: `--actor` flag, defaulting to the OS user (`getpass.getuser()`). This is attribution, not authentication — anyone with shell + DB access can claim any name. State that limitation in Completion Notes rather than implying an audit-grade trail.
3. **CLI framework.** Components leaves it open ("`typer` or stdlib `argparse`"). Recommended default: `argparse` — zero new dependencies to audit.
4. **AC1 says "prompts"; Components shows non-interactive `copilot approve <id>`.** Recommended default: both — interactive `review` satisfies AC1 literally; `approve`/`reject` satisfy Components and make scripting/tests easy.
5. **"Marks the proposal approved" with no status column.** Recommended default: the `ApprovalDecision` row *is* the mark. Do not add a status column to `diagnosis_proposals`.
6. **No doc says what happens to a `PipelineRun` on rejection.** AC3: "the run ends as a no-op". Recommended default: no change to `pipeline_runs` at all — the run already completed; the rejection is the terminal fact.
7. **How does the operator learn a proposal exists?** Nothing notifies anyone. Recommended default: `copilot pending` plus the `proposal_awaiting_approval` log line. Push notification is post-MVP.
