# Story 1.3: Runbook Corpus & Retrieval

## Status

Approved

## Story

**As an** on-call engineer,
**I want** the system to find the right runbook for an incoming alert,
**so that** diagnosis starts from the correct known failure mode instead of nothing.

## Acceptance Criteria

1. At least 10 runbooks (Markdown) exist, each describing one distinct failure mode.
2. Runbooks are embedded and stored in Chroma, accessible only through a single retrieval interface (NFR8) — nothing calls Chroma directly.
3. Given a test alert, the retrieval interface returns the correct runbook for at least 8/10 hand-labeled test cases.
4. Retrieval latency and the embedding model used are logged.

## Concepts You Need

_(Read this before starting — these are the ideas this story actually exercises, not generic background.)_

- **Why nothing outside `retrieval/` may import `chromadb`.** This is the NFR8 seam, and it exists for a concrete, dated reason: Story 5.1 swaps Chroma for Oracle DB 23ai, and that swap only stays a one-file change if every caller only ever talks to `retrieve_runbook`/`index_runbook`, never to a chromadb client directly. Same shape as Story 1.2's Repository-pattern rule for Postgres, one layer further out.
- **Embedding model consistency is not optional.** Whatever model embeds a runbook's content at index time **must** be the same model that embeds the alert's query text at retrieval time — different models produce vectors in different spaces, and a nearest-neighbor search across two different spaces is meaningless (it'll return *something*, just not the right thing, and nothing will throw an error to tell you). This is why AC4 requires logging which embedding model was used: an undetected silent mismatch is the single most common way RAG retrieval quietly degrades.
- **Scope boundary — this story is not Story 2.1.** `components.md` documents `retrieve_runbook(alert) -> Runbook | None`, with `None` returned "on low-confidence match, per Story 2.1 AC3." That confidence threshold does not exist yet. For this story, `retrieve_runbook` always returns its top-1 nearest match — the `| None` in the signature is future-proofing for Story 2.1 to add a threshold check inside, not something to build now.
- **This is a tiny, hand-rolled precursor to the real Eval Harness (Story 3.4).** AC3's "8/10 hand-labeled test cases" is the same idea as the 20-incident eval set, just scoped down to prove retrieval alone works before the full pipeline exists to evaluate end-to-end. Treat it with the same rigor: a hand-labeled fixture, not a cherry-picked example that happens to pass.
- **Note on this story's place in the roadmap:** still pre-cloud, like Story 1.2 — no AWS cert lab tie-in here either (the first one, G1/Bedrock Converse, lands in Story 2.1). This story also does **not** wire retrieval into the webhook/ingestion flow — `retrieve_runbook` is built and tested standalone; it gets called from the Diagnosis Graph's `retrieve` node starting in Story 2.2, not from this story's code.

### Data Model — `Runbook` (this story's scope only)

```
id                 TEXT PRIMARY KEY           -- stable slug, e.g. 'pod-crashloop-oom'
title              TEXT NOT NULL
content            TEXT NOT NULL              -- full markdown body; embedding lives in Chroma, keyed by this id
failure_mode_tags  TEXT[] NOT NULL DEFAULT '{}'
team               TEXT                        -- nullable, FR11 metadata -- not used by this story's retrieval logic yet
```
The vector embedding of `content` is **not** a field on this model — it's a Chroma index entry addressed by this model's `id`. [Source: architecture/database-schema.md, architecture/data-models.md#runbook]

### API / Interface Specification (this story's scope only)

No new HTTP endpoint. Two internal Python entrypoints in `retrieval/interface.py`:
- `index_runbook(runbook: Runbook) -> None`
- `retrieve_runbook(alert: Alert) -> Runbook | None` (always returns a `Runbook` in this story; `None` path is Story 2.1's addition)
[Source: architecture/components.md#retrieval-service]
