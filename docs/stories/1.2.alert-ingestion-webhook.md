# Story 1.2: Alert Ingestion Webhook

## Status

Ready for Review

## Story

**As an** on-call engineer,
**I want** the service to accept a simulated Prometheus alert and log it,
**so that** I have a durable, queryable record of every alert the system has seen.

## Acceptance Criteria

1. `POST /webhook/alert` accepts a JSON payload matching the simulated Prometheus alert schema and returns 202 Accepted.
2. Each received alert is persisted (id, payload, received_at) before any further processing.
3. A duplicate delivery of the same alert ID does not create a second record or trigger a second pipeline run (FR2).
4. Requests without a valid HMAC signature / shared-secret header are rejected with 401 before any processing (NFR9).
5. Unit tests cover: valid signed payload accepted, malformed payload rejected (4xx), unsigned/invalid-signature payload rejected (401), duplicate ID deduplicated.

## Concepts You Need

_(Read this before starting — these are the ideas this story actually exercises, not generic background.)_

- **HMAC signature verification must happen before anything else touches the request.** The order is: read raw bytes → verify signature → *then* parse/validate JSON → *then* touch any business logic. If you parse the JSON first and verify the signature second, you've already let an unauthenticated caller exercise your parser — a smaller attack surface, but still the wrong order. NFR9 AC4 says "before any processing" literally, not loosely.
- **Why dedup is a database `UNIQUE` constraint, not an `if exists: return` check in Python.** An earlier version of this design used a check-then-insert pattern — and it has a real race: two near-simultaneous duplicate deliveries can both pass the "does it exist?" check before either `INSERT` completes, producing two rows for one alert. The fix (already baked into the schema you're implementing against) is `external_alert_id UNIQUE` + `INSERT ... ON CONFLICT (external_alert_id) DO NOTHING` — the database itself makes the dedup atomic, so there's no window for the race to occur. This is a real concurrency bug class ("TOCTOU" — time-of-check to time-of-use) that shows up constantly in real systems, not just here.
- **First real persistence layer (Postgres via SQLAlchemy + Alembic).** Story 1.1 had no database. This story introduces the Repository pattern (`persistence/repositories.py`) as the *only* place allowed to touch the database — `api/`, `graph/`, and `approval/` call a repository method, never raw SQL/ORM queries. The point isn't ceremony — it's that when the vector store swaps (Story 5.1) or the schema changes, there's exactly one place to update.
- **Note on this story's place in the roadmap:** this is sprint **S1** territory, still pre-cloud. No AWS cert lab ties to this story — the first lab tie-in (G1, Bedrock Converse) lands in **Story 2.1**.
