# Story 4.3: Containerization & GitOps Deploy

## Status

Draft

## Story

As a platform operator,
I want the service deployed via Docker + Terraform + ArgoCD to a real cluster,
so that the product is a running, observable service, not something that only works on a laptop.

### Acceptance Criteria

1: The service is packaged as a Docker image, built in CI.
2: Terraform provisions the target infrastructure (OKE or equivalent) — no manually-created cloud resources.
3: ArgoCD deploys the service from Git repo state (GitOps) — no manual `kubectl apply` to the target environment (NFR2).
4: A deliberate failure (e.g., killing the pod) is demonstrated to auto-heal via the deployment controller, with a screenshot/log captured as proof.
5: Deployed service responds to a real webhook call end-to-end, not just locally.

3. **Story 3.2 keeps rate-limit and dedup state in process memory**, and Story 3.1's cache likewise. That forces a single replica (Known Gap #6). If either used Postgres or an external store, more replicas become possible.
4. **Story 4.1 will have added Langfuse settings** (host, keys) that the deployment must supply as secrets, and possibly a new table and migration.
5. **Story 4.2 will have added an `eval-gate` job** to the same `ci.yaml` this story adds an image build to; expect a merge of workflow changes.
6. **No Epic 3 story adds new required configuration** beyond what `config.py` holds today. Re-list every setting in both `Settings` classes before writing manifests.

## Concepts You Need

- **None of the deployment files exist yet.** `source-tree.md` shows `Dockerfile`, `infra/terraform/{main,oke,variables}.tf`, and `infra/argocd/application.yaml`. On `main` there is no `Dockerfile` and no `infra/` directory. `docker-compose.yaml` runs only Postgres. [Source: architecture/source-tree.md; verified by listing the repo]
- **The image cannot be built from the app directory alone.** `apps/incident-copilot/pyproject.toml` depends on `platform-core` through `[tool.uv.sources] platform-core = { path = "../../platform", editable = true }`. The Docker build context has to be the repository root (which is where `source-tree.md` puts the `Dockerfile`), and the build must install `platform/` as a real package, not an editable link to a path that will not exist in the final image.
- **Two different things heal a deployment, and AC4 names one of them.** Killing a pod is repaired by the Kubernetes Deployment/ReplicaSet controller, with or without ArgoCD. ArgoCD's `selfHeal` repairs drift between Git and the cluster (for example, someone editing the live Deployment). AC4 asks for the first ("via the deployment controller"). Demonstrating the second as well is worthwhile and optional.
- **ArgoCD has to get onto the cluster somehow, and "no manual `kubectl apply`" applies to that too.** Something must install ArgoCD and register the first Application before GitOps can take over. See Known Gap #4.
- **The service becomes a Kubernetes API client of the cluster it runs in.** `cluster/evidence.py` already tries `load_incluster_config()` first and falls back to kubeconfig. In-cluster, its permissions are whatever the pod's ServiceAccount is granted. This is the point where NFR5 (read-only) can be enforced by the cluster itself, not only by the code and its static-guard test. [Source: apps/incident-copilot/src/incident_copilot/cluster/evidence.py]
- **This is the first story that spends money on infrastructure and needs accounts the project does not have.** An OCI tenancy with permissions to create networking and OKE, and AWS credentials for Bedrock reachable from OCI compute, are prerequisites. Neither exists (Known Gaps #1, #2).
- **A webhook on a public address is a real attack surface.** HMAC verification (NFR9) is already implemented; the dev default secret `dev-only-insecure-secret-change-me` in `config.py` must never be what the deployed service runs with. [Source: apps/incident-copilot/src/incident_copilot/config.py, architecture/security.md]

## Dev Notes

### Previous Story Insights

- `GET /health` exists, defined inline in `main.py` (not in `api/health.py` as `source-tree.md` shows). It returns `{"status": "ok"}` unconditionally and does not check the database. Good enough for liveness; a readiness probe that passes while Postgres is unreachable will route webhooks to a pod that cannot store them. Moving the route or adding a DB check is in scope if Dev judges it necessary; note it as a deviation. [Source: apps/incident-copilot/src/incident_copilot/main.py, architecture/rest-api-spec.md]
- Chroma is used embedded (`chromadb.PersistentClient`, directory `./.chroma_data`), with no server. This is also why four `chromadb` advisories are ignored in `pip-audit`: they affect Chroma's HTTP server, which this project never runs. Deploying Chroma as a separate server to solve persistence would make those advisories applicable. [Source: .github/workflows/ci.yaml, apps/incident-copilot/src/incident_copilot/config.py]
- Chroma's default embedding model (`all-MiniLM-L6-v2`, ONNX) is downloaded on first use to `~/.cache/chroma/onnx_models`; CI caches it. A container with no outbound access to that download, or a read-only home directory, fails at first retrieval. [Source: .github/workflows/ci.yaml]
- Story 2.3's Kubernetes calls use a 10s timeout and degrade gracefully on any API failure, including a 403. A missing RBAC grant will therefore not crash the service; it will silently produce `grounded_in_live_state=False` on every run. Check the logs for `ClusterEvidenceError` warnings after deploying. [Source: apps/incident-copilot/src/incident_copilot/cluster/evidence.py, docs/qa/gates/2.3-read-only-kubectl-evidence-grounding.yml]
- boto3 reads AWS credentials from its standard chain; `platform_core/config.py` models only `aws_region` and `bedrock_model_id`. On OKE there is no AWS instance role, so credentials must arrive as environment variables from a Secret. [Source: platform/src/platform_core/config.py]
- Settings to supply today: app `environment`, `database_url`, `webhook_hmac_secret`, `chroma_persist_directory`, `chroma_collection_name`; platform `aws_region`, `bedrock_model_id`. [Source: apps/incident-copilot/src/incident_copilot/config.py, platform/src/platform_core/config.py]
- The dev sandbox used for Stories 2.2–2.3 had no `kind`/`kubectl`, and downloads of binaries were blocked. Expect the same for `terraform`, `docker`, and `oci`. Much of this story can only be verified in CI or by the user on their own machine.

## Known Gaps in Architecture Docs

1. **No OCI account or IAM setup exists.** Required before Task 4 can do anything real: a tenancy, a compartment, a user or group with policies to manage VCN, OKE, Object Storage, and Vault, API signing keys, and service limits that allow an OKE cluster and at least one worker node. Only the user can create these. **User prerequisite.**
2. **No AWS Bedrock credentials exist, and there is no plan for getting them into OKE.** The architecture mentions "IAM for Bedrock access from OCI compute" without a mechanism. Recommended default: a dedicated AWS IAM user limited to `bedrock:InvokeModel` on the one model, its access key held in OCI Vault and surfaced as a Kubernetes Secret. Without it the deployed service can ingest and retrieve but every run that reaches the propose node fails with `GatewayError`. **User prerequisite.**
3. **Image registry and tag-update flow are unspecified.** Recommended default: GHCR (no extra account; CI's `GITHUB_TOKEN` can push), images tagged with the commit SHA. For getting the new tag into the manifests ArgoCD watches: CI commits the tag bump to the manifests path on `main` after a successful push (simple, fully visible in Git; needs a guard so the bump commit does not retrigger itself). Alternative: ArgoCD Image Updater. If the GHCR package is private, the cluster needs an image pull secret.
4. **How ArgoCD is bootstrapped is unspecified.** Recommended default: Terraform installs ArgoCD via the Helm provider and creates the root Application, so the whole path from empty tenancy to synced app is `terraform apply` plus Git. This is the only reading under which "no manual `kubectl apply`" holds from the very first resource.
5. **Secret delivery into the cluster.** Security says "populated from a vault-backed source (e.g. OCI Vault)" and stops there. Recommended default: External Secrets Operator reading OCI Vault, with only `ExternalSecret` references in Git. Simpler alternative for M1: Sealed Secrets (encrypted values in Git, no vault). Either way, the user must supply the real secret values out of band.
6. **Replica count.** Not specified. Recommended default: `replicas: 1` with a `Recreate` strategy, because Chroma's embedded store on a single volume and any in-process cache/limiter/dedup state (Batch-Draft Assumption 3) are not safe to share across pods. Consequence to state openly: while the one pod restarts (including during AC4's demonstration) the webhook is briefly unavailable; auto-heal restores service, it does not prevent the gap.
7. **Chroma data and embedding model in a container.** Not specified. Recommended default: bake the embedding model into the image at build time, and index the runbook corpus at container start (or in the PreSync Job) into a PersistentVolumeClaim mounted at `chroma_persist_directory`. Indexing 10 runbooks at start is cheap and avoids a stale or empty index after a pod is replaced.
8. **How the webhook is exposed, and TLS.** Security says "TLS terminated at the OKE ingress/load balancer" with no detail. Recommended default for M1: a `LoadBalancer` Service (OCI load balancer). A proper TLS certificate needs a domain name the user controls; without one, the endpoint is plain HTTP on a public IP or uses a self-signed certificate. HMAC protects integrity and authenticity, not confidentiality. **User decision:** provide a domain, or accept HTTP for the demo and say so in the README.
9. **Where Postgres runs when deployed.** Not specified anywhere; locally it is a compose container. Options: in-cluster StatefulSet with a block volume (cheapest, self-managed, fits "single demo environment"), or OCI's managed PostgreSQL (more realistic, costs more, more Terraform). Recommended default: in-cluster StatefulSet. Related: Story 3.3's Approval CLI needs to reach this database; simplest is `kubectl exec` into the app pod to run it, which is a human using their own credentials, not the app.
10. **RBAC scope for cluster evidence.** Not specified. The service reads pods, events, and deployments in whatever namespace an alert names. Recommended default: a ClusterRole with `get`/`list` on exactly those three resources, bound cluster-wide to the app's ServiceAccount, since alerts can concern any namespace. Tighter alternative: a Role per monitored namespace.
11. **Who runs `terraform apply`, and where.** Not specified. Recommended default for M1: the user runs `plan` and `apply` from their own machine with their own OCI credentials; CI only runs `fmt` and `validate`. Putting OCI credentials into GitHub Actions to apply from CI is possible later and is a separate decision.
12. **Cost.** No doc estimates it. OKE worker nodes, a load balancer, block volumes, and possibly Vault and managed Postgres all bill while they exist, and OCI's Always Free allowances may or may not cover this shape. Dev must not assume it is free: before the first `apply`, produce an itemised estimate from OCI's current price list for the planned shapes and get the user's approval. **User decision (spend).**
13. **"OKE or equivalent."** AC2 permits an equivalent. If the OCI account is not ready when this story is reached, the cheapest honest fallback is a different managed Kubernetes the user already has access to. A local kind cluster would satisfy AC3 and AC4 mechanically but not AC2 (Terraform provisioning real infrastructure) or AC5 ("not just locally"). **User decision.**
