# Story 3.1: LLM Response Caching (LRU)

## Status

Draft

## Story

As a platform operator,
I want LLM/embedding responses cached,
so that repeated identical calls don't re-incur cost/latency and we have a benchmarked hit-rate number to quote.

### Acceptance Criteria

1: The LLM gateway caches responses for identical (model, prompt) pairs using an LRU eviction policy with a configurable max size.
2: Cache hit-rate is measured and reported via a benchmark against a fixture set of repeated/near-repeated queries.
3: Cache is transparent to callers — no call site needs to know whether a response was cached or live.
4: Unit tests cover cache hit, cache miss, eviction under capacity pressure.

## Concepts You Need

- **This is the first Epic 3 story and the first time `platform/` gets a second module.** Today the gateway is exactly two files: `gateway.py` (`complete()`, retry, `GatewayError`) and `bedrock_provider.py` (the only `boto3` importer). `cache.py` is named in the Source Tree but does not exist yet. [Source: architecture/source-tree.md; verified by listing `platform/src/platform_core/gateway/`]
- **"Transparent" (AC3) has a concrete meaning here: `complete(prompt, model_config) -> LLMResponse` does not change.** There are exactly two call paths into it today (`propose_diagnosis` in `graph/nodes/propose.py`, and soon Story 3.4's judge). Neither may need an edit for this story to be done. If you find yourself touching `propose.py`, you've broken AC3.
- **LRU is "least recently *used*", not "oldest inserted".** A cache *hit* must move the entry to the most-recent position, or a hot entry gets evicted behind cold ones. This is the single most common LRU bug and is exactly what AC4's "eviction under capacity pressure" test should prove (insert A, B; read A; insert C at capacity 2 — B must be the one evicted, not A).
- **Only successes are cached.** A `GatewayError` must never be stored — caching a failure would turn one transient Bedrock blip into a permanent wrong answer for that prompt.
- **An exact-match cache gets zero hits on "near-repeated" queries, and that's the honest result AC2 should report**, not something to engineer around. A semantic/fuzzy cache is a different (much riskier) feature: for a diagnosis product, returning pod A's cached diagnosis for pod B's alert is a correctness bug. See Known Gap #3.

## Tasks / Subtasks

- [ ] **Task 1: Build the LRU cache module (AC: 1, 4)**
  - [ ] Create `platform/src/platform_core/gateway/cache.py` with a small `LRUCache` class: `get(key) -> str | None`, `put(key, value) -> None`, `stats() -> CacheStats` (hits, misses, evictions, size, `hit_rate`), `clear()`. Implement on `collections.OrderedDict` (`move_to_end` on hit, `popitem(last=False)` on overflow) — stdlib only, no new dependency. [Source: architecture/source-tree.md, architecture/components.md#llm-gateway-platform]
  - [ ] Guard mutations with a `threading.Lock` — the webhook process is multi-threaded under Uvicorn, and Story 3.2 may hand pipeline runs to background tasks.
  - [ ] Cache key is the tuple `(model_id, prompt)` exactly — no normalization, no hashing needed (see Known Gap #2).
  - [ ] Add `llm_cache_max_size: int` (recommended default 256) and `llm_cache_enabled: bool = True` to `platform/src/platform_core/config.py`'s `Settings` — never a hardcoded constant in `cache.py`. [Source: architecture/coding-standards.md#critical-rules]
  - [ ] A `max_size` of 0 (or `llm_cache_enabled=False`) must mean "caching off", not an error or an unbounded cache.
  - [ ] Unit tests `platform/tests/unit/test_cache.py`: hit; miss; eviction under capacity pressure (including the read-refreshes-recency case above); overwrite of an existing key doesn't grow the cache; stats counters are correct; disabled/zero-size behaves as a no-op.

- [ ] **Task 2: Wire the cache into `complete()` (AC: 1, 3)**
  - [ ] In `gateway.py`, look up `(model_config.model_id, prompt)` **before** the retry loop; on hit return `LLMResponse(content=cached)` without calling `converse`. On a live success, store the text, then return.
  - [ ] Never cache on any exception path (`GatewayError` from provider failure or malformed response shape).
  - [ ] `complete()`'s signature and `LLMResponse`'s existing `content` attribute stay unchanged. Do not modify `propose.py` or any other call site.
  - [ ] Expose `cache_stats()` (module-level function in `gateway.py` or re-exported from `cache.py`) so the benchmark, and later Story 4.1, can read hit-rate without reaching into a private global.
  - [ ] Unit tests in `platform/tests/unit/test_gateway.py`: second identical call does not call `converse` (assert `call_count == 1`); different prompt → miss; same prompt + different `model_id` → miss; a failed call is not cached (next call hits the provider again); all five existing gateway tests still pass — note they share a module-level cache, so add an autouse fixture that clears it between tests.

- [ ] **Task 3: Hit-rate benchmark (AC: 2)**
  - [ ] Create a fixture set (`platform/tests/fixtures/cache_benchmark_queries.py`, plain Python data per Test Strategy) of ~50 prompts mixing: exact repeats, near-repeats (same template, one label value changed), and unique prompts — with the mix documented in the file so the resulting number is interpretable.
  - [ ] Create `platform/tests/unit/test_cache_benchmark.py` that replays the fixture through `complete()` with `converse` mocked, asserts the measured hit-rate equals the analytically expected value for that fixture, and prints/logs the number. Mocked `converse` is correct here: the benchmark measures cache behaviour, not Bedrock.
  - [ ] Report the number (and the fixture mix it came from) in Completion Notes. State explicitly that near-repeats scored as misses and why.
  - [ ] Also run the fixture at two cache sizes (e.g. one below the number of distinct prompts, one above) so the report shows eviction's effect on hit-rate, not just the best case.

- [ ] **Task 4: Full validation**
  - [ ] `cd platform && uv run ruff check . && uv run bandit -r src -q && uv run pytest tests/unit -q && uv run pip-audit`
  - [ ] `cd apps/incident-copilot && uv run pytest tests/unit -q` — the app's `propose` tests mock `complete`, so they should be unaffected; confirm rather than assume.

## Known Gaps in Architecture Docs

1. **The story says "LLM/embedding responses", but embeddings never go through the gateway.** They are computed inside `retrieval/chroma_backend.py` by Chroma's local ONNX model — no network cost, and behind the NFR8 seam that nothing else may reach into. Recommended default: scope this story to gateway LLM responses only (which is all AC1 actually specifies) and say so in Completion Notes. Do not route embeddings through the gateway to make the story title literally true.
2. **No doc says whether the cache key should be normalized** (whitespace, case). Recommended default: exact `(model_id, prompt)` match. Normalizing is a behaviour change that could conflate genuinely different prompts.
3. **"Near-repeated queries" (AC2) is undefined.** Recommended default: include them in the benchmark fixture and report them as misses. No semantic cache.
4. **No logging library exists in `platform/`.** Recommended default: expose counters via `cache_stats()` and add no logging and no new dependency in this story; Story 4.1 (tracing) is where gateway observability is designed properly.
5. **No TTL / invalidation is specified.** A cached diagnosis for a prompt stays valid only as long as the runbook text inside that prompt is unchanged — which is automatically true, because the runbook content is *part of the prompt*, so an edited runbook produces a different key. Live evidence (Story 2.3) is also in the prompt, so stale-cluster-state reuse cannot happen either. Recommended default: no TTL; document this reasoning.
6. **Process-local scope is not stated anywhere.** With more than one worker process each has its own cache, and the cache is empty after every restart. Recommended default: accept for MVP and state it next to the quoted hit-rate so nobody reads it as a fleet-wide number.

## Batch-Draft Assumptions (revalidate before development)

This story was drafted in a batch with 3.2–3.4, before any of them was implemented. It is first in sequence, so it depends on no unbuilt sibling — but the siblings depend on these decisions, so changing any of them means re-checking the named story:

- **Cache lookup happens before any rate-limit accounting** → Story 3.2 assumes a cache hit consumes no token.
- **`complete()`'s signature is unchanged and `LLMResponse` gains no required field** → Stories 3.2 and 3.4 are written against today's signature.
- **`cache_stats()` exists as a public accessor** → Story 4.1 may read it.
- **The cache is a module-level singleton that tests must clear** → Stories 3.2 and 3.4 inherit the same autouse-fixture need in any test that calls `complete()` un-mocked.
- **Re-verify at development time** that `gateway.py` on `main` still matches what was read while drafting (retry loop, `GatewayError`, `ModelConfig`), since nothing else is scheduled to touch it first.
