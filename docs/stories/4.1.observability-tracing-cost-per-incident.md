# Story 4.1: Observability: Tracing & Cost-per-Incident

## Status

Draft

## Story

As a platform operator,
I want every LLM call traced and cost-per-incident computed,
so that I can answer "what does one diagnosis cost" with a real number, not an estimate.

### Acceptance Criteria

1: Every LLM gateway call is traced (Langfuse or LangSmith) with model, token counts, latency, and cost recorded.
2: A cost-per-incident metric is computed by aggregating trace data per pipeline run and reported.
3: Traces never contain secrets/PII (NFR7/FR10) — verified by a test asserting no raw kubeconfig/API key appears in a trace payload.
4: The cost-per-incident number from a test run is captured in README/docs as a quotable figure.

## Batch-Draft Assumptions (revalidate before development)

This story was drafted on 2026-11-16 in a batch with all of Epics 3 and 4, **before any Epic 3 story was implemented**. Everything in "Dev Notes" about current code was verified against `main` at commit `0652292` (Epic 2 complete). The items below are assumptions about work that did not exist yet. Before development starts, re-read the Dev Agent Records of Stories 3.1–3.4 and correct this story wherever they differ (`validate-next-story` exists for exactly this).

1. **Story 3.1 will have added an LRU cache inside `platform_core/gateway/`** (`cache.py` per `source-tree.md`), in front of the provider call, transparent to callers. Assumed consequence: a cache hit makes no provider call, so it has zero provider cost and no provider token usage. This story's tracing design depends on where exactly the cache check sits in `complete()`.
2. **Story 3.2 will have added a token-bucket limiter** (`rate_limiter.py`) in the same module, and possibly the circuit breaker Story 2.1 deferred. Assumed: a request rejected by the limiter raises `GatewayError` (or a subclass) before any provider call.
3. **Story 3.4's eval harness will call `complete()` for judge calls outside any pipeline run**, so some traced calls have no `pipeline_run_id`.
4. **`complete(prompt, model_config) -> LLMResponse` keeps its current signature.** If 3.1/3.2 changed it (for example to add a cache-bypass flag), the tasks below that touch `complete()` need re-reading.
5. **No Epic 3 story will have added `langfuse` or touched `platform_core/tracing/`.** Verified empty today; assumed still empty.

## Concepts You Need

- **The token counts you need are already being returned by Bedrock and thrown away.** `bedrock_provider.converse()` returns only `response["output"]["message"]["content"][0]["text"]`. The Converse response also carries a `usage` block (`inputTokens`, `outputTokens`, `totalTokens`) and `metrics.latencyMs`. AC1 cannot be met without changing what `converse()` returns, and `LLMResponse` currently has exactly one field (`content`). [Source: platform/src/platform_core/gateway/bedrock_provider.py, platform/src/platform_core/gateway/gateway.py]
- **`platform_core/tracing/` exists but is an empty package**, and `langfuse` is not a dependency of `platform/` or `apps/incident-copilot/`. This story builds the tracing module from nothing. [Source: platform/src/platform_core/tracing/__init__.py, platform/pyproject.toml]
- **The gateway does not know which pipeline run it is serving.** `pipeline_run_id` is bound in the app with `structlog.contextvars.bind_contextvars` inside `run_pipeline`; `platform/` has no `structlog` dependency and `complete()` takes no run identifier. AC2 ("aggregating trace data per pipeline run") needs that link, and no architecture doc says how it crosses the `apps/` → `platform/` boundary. See Known Gap #2.
- **Cost is not something Bedrock returns.** The API returns token counts; cost is tokens multiplied by a per-model price that this project has to hold somewhere. See Known Gap #3.
- **A trace is the easiest place in this system to leak data.** The prompt sent to the model contains alert labels/annotations, the full runbook body, and (since Story 2.3) live cluster evidence. Ingestion already scrubs PII before persistence (FR10), but AC3 asks for a test on the trace payload itself, not a reliance on the upstream scrubber. [Source: architecture/coding-standards.md#critical-rules, architecture/security.md#data-protection]
- **Bedrock credentials are still not configured in any environment this project uses.** Every LLM call so far has been mocked. AC1–AC3 can be built and tested with mocks; AC4 cannot (see Known Gap #6).

## Tasks / Subtasks

- [ ] **Task 1: Carry usage data out of the provider (AC: 1)**
  - [ ] Change `bedrock_provider.converse()` to return the text plus `usage.inputTokens`, `usage.outputTokens`, and `metrics.latencyMs` from the Converse response (a small pydantic model or dataclass, not a bare tuple or dict). Keep its contract of raising raw `botocore` exceptions for `gateway.py` to translate.
  - [ ] Extend `LLMResponse` additively: `content` stays; add `model_id`, `input_tokens`, `output_tokens`, `latency_ms`, `cost_usd`, and (if Story 3.1 landed as assumed) `cached: bool`. Every existing caller reads only `.content`, so nothing downstream changes.
  - [ ] A missing `usage` block must go through the existing `KeyError` → `GatewayError` path (QA Story 2.1 REL-001), or be treated as "usage unknown" — pick one and test it. Do not let it produce a silent zero cost.
  - [ ] Update `platform/tests/unit/test_bedrock_provider.py` and `test_gateway.py`; all existing tests must still pass.

- [ ] **Task 2: Price table and cost calculation (AC: 1, 2)**
  - [ ] Add a per-model price table (USD per 1K input tokens, per 1K output tokens) read through `platform_core/config.py`, per Known Gap #3. An unknown model ID must be reported as "cost unknown", never as `0.0`.
  - [ ] Unit tests: known model computes correctly; unknown model is flagged; a cache hit costs nothing at the provider.

- [ ] **Task 3: Build `platform_core/tracing/langfuse_wrapper.py` (AC: 1, 3)**
  - [ ] Add `langfuse` as an explicit dependency of `platform/pyproject.toml`. `tech-stack.md` says "2.x"; re-verify the current release on PyPI before pinning, as Stories 2.2 and 2.3 did for `langgraph` and `kubernetes`. [Source: architecture/tech-stack.md, architecture/source-tree.md]
  - [ ] Expose one function that the gateway calls once per `complete()` call, recording: model ID, input/output tokens, latency, cost, outcome (success, cache hit, rate-limited, failed after retries), attempt count, and the correlation ID from Task 4.
  - [ ] Langfuse host and keys come from `platform_core/config.py` only. When they are not set, tracing is a no-op and the gateway works exactly as before, so unit tests, CI, and local runs need no Langfuse instance.
  - [ ] A failure inside the tracing call (Langfuse unreachable, SDK error) must never fail or delay the LLM call it describes. Catch it inside the wrapper and log a warning.
  - [ ] Decide and document what prompt/response content the trace carries, per Known Gap #4.

- [ ] **Task 4: Link traces to pipeline runs (AC: 2)**
  - [ ] Implement the correlation mechanism from Known Gap #2 so every trace emitted during `run_pipeline` carries that run's `pipeline_run_id`, and calls made outside a run (eval judge calls) carry none.
  - [ ] Unit test in `apps/incident-copilot`: a pipeline run with the gateway mocked at the provider boundary produces a trace record tagged with the run's ID.

- [ ] **Task 5: Cost-per-incident metric (AC: 2)**
  - [ ] Implement an aggregation that, given a `pipeline_run_id`, sums cost and tokens across that run's traced calls, and a report over a set of runs (count, total, mean, min, max cost per run). Source of the data per Known Gap #5.
  - [ ] Make it runnable as one command, and state in its output how many runs had unknown cost.
  - [ ] Unit tests: a run with one call; a run with zero LLM calls (no runbook matched, so Story 2.1's guard never called the gateway) costs 0 and is counted, not dropped; a run with a cache hit.

- [ ] **Task 6: No-secrets-in-traces test (AC: 3)**
  - [ ] Add a test that captures the exact payload the wrapper would send to Langfuse for a pipeline run whose alert payload, environment, and config contain planted sentinel values (a fake AWS secret key, a fake kubeconfig token, a fake webhook HMAC secret, an email address and IP in an alert annotation), and asserts none of the sentinels appear anywhere in the serialized trace.
  - [ ] This is security test (2) named in Test Strategy; it runs in the normal unit tier. [Source: architecture/test-strategy-and-standards.md#continuous-testing]

  - [ ] If real access is not available when this story is developed, do not publish a number computed from mocked token counts. Leave AC4 open and say so in Completion Notes.

## Dev Notes

### Previous Story Insights

- Story 2.1 built `complete()` with retry and timeout only, and deliberately deferred the circuit breaker to Story 3.2. A single `complete()` call can make up to 3 provider attempts; a trace should describe the call as the caller saw it and record the attempt count. [Source: platform/src/platform_core/gateway/gateway.py]
- Story 2.1's `propose_diagnosis` returns `matched=False` without calling the gateway when no runbook clears the threshold. Those runs have zero LLM calls and zero cost; they are real incidents and belong in the average. [Source: apps/incident-copilot/src/incident_copilot/graph/nodes/propose.py]
- Story 2.2 noted `retrieve_runbook` runs twice per pipeline run. That is embedding work in local Chroma, not a gateway call, so it does not appear in LLM cost. Embedding cost is out of scope here (Chroma's default embedding model runs locally, cached in CI as `all-MiniLM-L6-v2`). [Source: docs/stories/2.2.langgraph-state-machine-refactor.md#completion-notes-list, .github/workflows/ci.yaml]
- `PipelineRun.llm_provider_config` currently stores the Bedrock model ID (`amazon.nova-micro-v1:0`), not the literal `bedrock` the data model describes. Either is usable as a grouping key for cost reports. [Source: apps/incident-copilot/src/incident_copilot/graph/pipeline.py, architecture/data-models.md#pipelinerun]
- Bedrock credentials have not been configured since Story 2.1; the gateway is mocked in both unit and integration tiers by design. [Source: architecture/test-strategy-and-standards.md#integration-tests]

### Data Models

- No table for traces or cost exists in `architecture/database-schema.md`, and `PipelineRun` has no cost column. See Known Gap #5 before adding one.
- `LLMResponse` and `ModelConfig` are plain classes in `gateway.py`, not pydantic models. Coding Standards ask for pydantic for anything crossing a module boundary; converting `LLMResponse` while extending it is in scope. [Source: architecture/coding-standards.md#language-specific-guidelines]

### API / Interface Specification

- `complete(prompt, model_config) -> LLMResponse` — signature unchanged; return type gains fields.
- `converse(prompt, model_id, timeout_seconds)` — return type changes from `str` to a structured result. Its only caller is `gateway.py`.
- New: the tracing wrapper's record function, and the cost-per-incident aggregation and its command.
- Components says the gateway "emits traces" and depends on Langfuse "(emits trace per call)". [Source: architecture/components.md#llm-gateway-platform]

### Coding Standards (relevant excerpts)

- Never import `boto3` outside `platform/gateway/`; `botocore.exceptions.*` caught only there.
- Never log or trace a raw alert payload, kubeconfig, or API key. Scrub first.
- All config and secrets through `config.py`; no `os.environ.get(...)` elsewhere.
- `structlog` only, no `print()`.
  [Source: architecture/coding-standards.md#critical-rules]

### Testing

- Unit tests mock boto3 and never touch a network; the Langfuse client is an external dependency and is mocked the same way. [Source: architecture/test-strategy-and-standards.md#unit-tests]
- Integration tier keeps the gateway mocked, so no integration test produces real token counts. [Source: architecture/test-strategy-and-standards.md#integration-tests]
- 80% line coverage target applies to `platform/gateway/`. [Source: architecture/test-strategy-and-standards.md#testing-philosophy]

### Technical Constraints

- Tracing must be optional at runtime: no Langfuse configuration means no tracing and no error.
- Do not add a second tracing vendor. The PRD allows "Langfuse or LangSmith"; the architecture chose Langfuse. [Source: architecture/tech-stack.md]
- Do not change the retry, timeout, or error-translation behaviour of `complete()`.
- Do not publish a cost figure that was not measured against the real provider.

## Known Gaps in Architecture Docs

1. **Langfuse hosting is undecided.** `tech-stack.md` says "2.x (self-hosted or cloud)". Recommended default: Langfuse Cloud free tier for M1, because self-hosting adds a Postgres-backed service to run and, after Story 4.3, to deploy. This sends prompt-derived data to a third party, which makes Known Gap #4 matter more. **User decision.**
2. **How `pipeline_run_id` reaches the gateway is not specified.** Recommended default: a `contextvars.ContextVar` owned by `platform_core/tracing/`, with a small context manager that `run_pipeline` enters alongside its existing `structlog.contextvars` binding. This keeps `complete()`'s signature unchanged (so `propose.py` and every other call site is untouched) and keeps `platform/` free of any import from `apps/`. Alternative: an explicit `trace_context` argument on `complete()`, which is more visible but changes every call site.
3. **No doc says where model prices live.** Recommended default: a mapping in `platform_core/config.py` keyed by model ID with the price date in a comment, overridable by environment. Dev must take the current Amazon Nova Micro price from the AWS Bedrock pricing page at implementation time and cite the date; do not rely on a remembered figure. Langfuse can also compute cost from its own model table, but then the quotable number depends on a third party's price list.
4. **Whether traces carry prompt and response text is not specified.** Coding Standards forbid tracing a raw alert payload; the prompt is built from alert labels and annotations, the runbook body, and cluster evidence. Recommended default: by default send metadata only (model, tokens, latency, cost, outcome, run ID); allow prompt/response capture behind an explicit config flag, and when on, pass content through a redaction step. AC3's test must pass in both modes.
5. **Where cost-per-incident is computed from is not specified.** AC2 says "aggregating trace data per pipeline run". Options: (a) query Langfuse's API by run ID, which needs a reachable Langfuse to produce the number; (b) also persist per-call usage locally. Recommended default: (b), a small `llm_calls` table (run ID nullable, model, tokens, cost, latency, outcome, timestamp) with its own repository and Alembic migration, written by the app via a callback the tracing wrapper invokes. The table is new schema not in `database-schema.md`; note it as a deviation. If the user prefers no new table, fall back to (a).
6. **AC4 needs real Bedrock calls and nobody has credentials yet.** A "test run" that produces a quotable cost requires an AWS account with Bedrock model access enabled for the chosen model and region, and credentials available to the machine running it. This has been open since Story 2.1. Recommended: develop Tasks 1–6 and 8 with mocks, and treat Task 7 as blocked until the user provides access. **User decision / prerequisite.**
7. **Cache hits and rate-limited calls: traced or not?** No doc says. Recommended default: trace both with an explicit outcome and zero provider cost, so cost-per-incident and Story 3.1's hit-rate can be reconciled from the same data. Depends on Batch-Draft Assumptions 1 and 2.
