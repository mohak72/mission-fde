# Story 2.2: LangGraph State Machine Refactor

## Status

Approved

## Story

**As a** developer,
**I want** the diagnosis pipeline rebuilt as an explicit LangGraph state machine (classify → retrieve → propose → human-approval),
**so that** each stage is independently testable and the pipeline's state is inspectable rather than hidden inside one function.

## Acceptance Criteria

1. Pipeline implemented as a LangGraph graph with distinct nodes: classify alert type, retrieve runbook, investigate (placeholder until Story 2.3), propose diagnosis+action, human-approval (stub returning "pending" until Epic 3).
2. Each node is unit-testable in isolation with mocked inputs/outputs.
3. Running an alert through the graph end-to-end produces the same diagnosis output as the pre-refactor Story 2.1 loop — verified by a regression fixture comparing old vs. new output on the same test alerts.
4. Graph state/transitions are logged so a run can be replayed/debugged from the log alone.

## Concepts You Need

_(Read this before starting — these are the ideas this story actually exercises, not generic background.)_

- **Why `propose.py` already exists.** Story 2.1 built `graph/nodes/propose.py`'s `propose_diagnosis(alert, session) -> DiagnosisResult` *deliberately ahead of this story*, specifically so this refactor would **wrap** it, not reimplement it — its own docstring says so ("placed here ahead of Story 2.2's LangGraph refactor, which will wrap this into an actual graph node"). This is the central design constraint of this story: AC3's regression check is trivially satisfiable (and actually meaningful as a safety net, not security theater) only if the graph's propose node calls the existing function rather than duplicating its logic. The same applies to `retrieve_runbook` (Story 1.3/2.1) for the retrieve node.
- **Why this story introduces `PipelineRun` and `DiagnosisProposal` persistence, even though no AC says "persist."** `components.md` states the Diagnosis Graph "Owns `PipelineRun` lifecycle and produces `DiagnosisProposal`" — and Story 2.1's own Dev Notes explicitly deferred `DiagnosisProposal` persistence to "once a `PipelineRun` exists for it to reference," i.e., this story. AC4 ("graph state/transitions are logged so a run can be replayed") is specifically about the `pipeline_runs.node_transitions` column — there's no way to satisfy AC4 as a *durable, replayable* guarantee (vs. just structlog output disappearing after the process exits) without the `PipelineRun` row existing. [Source: architecture/components.md#diagnosis-graph, architecture/data-models.md#pipelinerun, docs/stories/2.1.llm-triage-summary.md]
- **Why the investigate and human-approval nodes are stubs, not empty.** AC1 explicitly calls them out as placeholders ("investigate (placeholder until Story 2.3)", "human-approval (stub returning 'pending' until Epic 3)") — building real behavior here would be scope creep into Story 2.3/3.3. The stub still has to be a real node in the graph (so the state machine's shape is correct and Story 2.3 only has to swap the node body, not restructure the graph) — it just does nothing externally observable yet.
- **What "classify alert type" means here is genuinely underspecified** — see Known Gaps below. Don't invent an ML classifier; this project's repeated pattern (regex PII scrubbing over an ML service, empirical threshold over a learned one) is "right-sized, not novel," and classify should follow that same instinct.
- **Error propagation stays exactly as Error Handling Strategy already specifies**: nodes don't each wrap their own try/except — a node either degrades gracefully in-graph (no node in *this* story does; that's Story 2.3's `ClusterEvidenceError` pattern) or lets its exception propagate, and `run_pipeline`'s outer loop is what catches it, marks `PipelineRun.status = 'failed'`, logs with `pipeline_run_id`, and re-raises nothing further. This means `GatewayError` (including the Story 2.1 QA fixes — REL-001/REL-002 — for malformed Bedrock responses/LLM output) and `RetrievalError`-shaped failures flow through this story's graph exactly as they already flow through direct function calls today — the refactor changes *where* `propose_diagnosis`/`retrieve_runbook` are called from, not their failure contract. [Source: architecture/error-handling-strategy.md#error-propagation]

- [ ] Task 3: Wire the LangGraph state machine (AC: 1, 4)
  - [ ] Re-verify `langgraph`'s current PyPI version before pinning (architecture names `1.2.14` as of 2026-11-04 — same "verify current, don't trust the doc blindly" discipline as Story 2.1's `boto3` check) [Source: architecture/tech-stack.md]
  - [ ] Define the graph state shape (fields at minimum: `alert`, `alert_type`, `runbook`, `diagnosis` (`DiagnosisResult`), `grounded_in_live_state`, `approval_status`)
  - [ ] Build `graph/pipeline.py`: a `StateGraph` wiring `classify → retrieve → investigate → propose → approve`, and `run_pipeline(alert: Alert, session: Session) -> PipelineRun` — the one entry point both the webhook path and the future MCP tool call into [Source: architecture/components.md#diagnosis-graph]. **Note:** `components.md`'s documented signature is `run_pipeline(alert: Alert) -> PipelineRun` (no `session`) — deviate and keep `session` explicit, consistent with every other seam in this codebase (`retrieve_runbook(alert, session)`, `propose_diagnosis(alert, session)`); document this as an intentional deviation, not an oversight.
  - [ ] `run_pipeline` creates the `PipelineRun` row first (status=`running`), runs the graph, appends a `node_transitions` entry as each node enters/exits (via `PipelineRunRepository.append_transition`, committed independently per node — no single long-lived transaction across the whole run) [Source: architecture/error-handling-strategy.md#data-consistency]

  - [ ] Every log line emitted during a run includes `pipeline_run_id` (structlog), per Error Handling Strategy's Logging Standards — this is what makes AC4's "replayable from the log alone" true even without re-reading the DB row [Source: architecture/error-handling-strategy.md#logging-standards]

## Dev Notes

### Previous Story Insights

- Story 2.1 built `graph/nodes/propose.py` specifically so this story could wrap it — reuse `propose_diagnosis(alert, session) -> DiagnosisResult` unchanged. [Source: docs/stories/2.1.llm-triage-summary.md]
- Story 2.1's QA review added two fixes that matter here: `gateway.complete()` now raises `GatewayError` (not a raw `KeyError`/`IndexError`) on a malformed Bedrock response, and `propose._parse_response()` now raises `GatewayError` (not a silent empty result) on a non-conforming LLM response. Both exceptions will now propagate through this story's graph exactly as described in Error Handling Strategy — no new handling needed in the propose node itself, just confirm `run_pipeline`'s outer catch covers it.
- AWS Bedrock credentials are still not configured as of Story 2.1's completion — same implication here: this story's tests are fully satisfiable with the Gateway mocked (per Test Strategy), same as Story 2.1. If Dev reaches a point where a real Bedrock call is genuinely required, halt and ask — same rule as Story 2.1.
- Story 1.3's confidence threshold (`CONFIDENCE_DISTANCE_THRESHOLD = 0.5`) and Story 2.1's model choice (`amazon.nova-micro-v1:0`) are unchanged by this refactor — this story moves *where* these are called from, not their behavior.

## Known Gaps in Architecture Docs

1. **What "classify alert type" actually produces** — the epic names the node but no PRD/architecture doc defines a taxonomy, an output schema, or whether this is rule-based or ML-based. Dev picks and documents a right-sized scope (recommended: simple metadata extraction from the existing `alertname` label, no new ML/LLM call — consistent with this project's repeated preference for the simplest approach that satisfies the AC, e.g. regex PII scrubbing over an ML service).
2. **`run_pipeline`'s documented signature omits `session`** (`components.md` shows `run_pipeline(alert: Alert) -> PipelineRun`) — every other seam in the codebase threads `session` explicitly; Dev should keep doing so here and document the deviation rather than silently matching the doc's incomplete signature.
3. **No persisted representation of "awaiting human approval" exists yet** — `pipeline_runs.status` only has `running`/`completed`/`failed`, and `approval_decisions` doesn't exist until Story 3.3. Dev's call (recommended: `status='completed'` means the *run* finished, independent of whether a human has acted on its proposal yet — don't add a new status value or table ahead of Story 3.3 needing one).
4. **LangGraph 1.2.14's exact node/state API** — tech-stack.md names the library and version but the architecture docs don't specify `StateGraph` usage patterns; Dev should verify current API against LangGraph's own docs at implementation time, same discipline as every other library version check in this project.
