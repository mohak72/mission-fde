# Story 2.2: LangGraph State Machine Refactor

## Status

Ready for Review

## Story

**As a** developer,
**I want** the diagnosis pipeline rebuilt as an explicit LangGraph state machine (classify → retrieve → propose → human-approval),
**so that** each stage is independently testable and the pipeline's state is inspectable rather than hidden inside one function.

## Acceptance Criteria

1. Pipeline implemented as a LangGraph graph with distinct nodes: classify alert type, retrieve runbook, investigate (placeholder until Story 2.3), propose diagnosis+action, human-approval (stub returning "pending" until Epic 3).
2. Each node is unit-testable in isolation with mocked inputs/outputs.
3. Running an alert through the graph end-to-end produces the same diagnosis output as the pre-refactor Story 2.1 loop — verified by a regression fixture comparing old vs. new output on the same test alerts.
4. Graph state/transitions are logged so a run can be replayed/debugged from the log alone.

## Concepts You Need

_(Read this before starting — these are the ideas this story actually exercises, not generic background.)_

- **Why `propose.py` already exists.** Story 2.1 built `graph/nodes/propose.py`'s `propose_diagnosis(alert, session) -> DiagnosisResult` *deliberately ahead of this story*, specifically so this refactor would **wrap** it, not reimplement it — its own docstring says so ("placed here ahead of Story 2.2's LangGraph refactor, which will wrap this into an actual graph node"). This is the central design constraint of this story: AC3's regression check is trivially satisfiable (and actually meaningful as a safety net, not security theater) only if the graph's propose node calls the existing function rather than duplicating its logic. The same applies to `retrieve_runbook` (Story 1.3/2.1) for the retrieve node.
- **Why this story introduces `PipelineRun` and `DiagnosisProposal` persistence, even though no AC says "persist."** `components.md` states the Diagnosis Graph "Owns `PipelineRun` lifecycle and produces `DiagnosisProposal`" — and Story 2.1's own Dev Notes explicitly deferred `DiagnosisProposal` persistence to "once a `PipelineRun` exists for it to reference," i.e., this story. AC4 ("graph state/transitions are logged so a run can be replayed") is specifically about the `pipeline_runs.node_transitions` column — there's no way to satisfy AC4 as a *durable, replayable* guarantee (vs. just structlog output disappearing after the process exits) without the `PipelineRun` row existing. [Source: architecture/components.md#diagnosis-graph, architecture/data-models.md#pipelinerun, docs/stories/2.1.llm-triage-summary.md]
- **Why the investigate and human-approval nodes are stubs, not empty.** AC1 explicitly calls them out as placeholders ("investigate (placeholder until Story 2.3)", "human-approval (stub returning 'pending' until Epic 3)") — building real behavior here would be scope creep into Story 2.3/3.3. The stub still has to be a real node in the graph (so the state machine's shape is correct and Story 2.3 only has to swap the node body, not restructure the graph) — it just does nothing externally observable yet.
- **What "classify alert type" means here is genuinely underspecified** — see Known Gaps below. Don't invent an ML classifier; this project's repeated pattern (regex PII scrubbing over an ML service, empirical threshold over a learned one) is "right-sized, not novel," and classify should follow that same instinct.
- **Error propagation stays exactly as Error Handling Strategy already specifies**: nodes don't each wrap their own try/except — a node either degrades gracefully in-graph (no node in *this* story does; that's Story 2.3's `ClusterEvidenceError` pattern) or lets its exception propagate, and `run_pipeline`'s outer loop is what catches it, marks `PipelineRun.status = 'failed'`, logs with `pipeline_run_id`, and re-raises nothing further. This means `GatewayError` (including the Story 2.1 QA fixes — REL-001/REL-002 — for malformed Bedrock responses/LLM output) and `RetrievalError`-shaped failures flow through this story's graph exactly as they already flow through direct function calls today — the refactor changes *where* `propose_diagnosis`/`retrieve_runbook` are called from, not their failure contract. [Source: architecture/error-handling-strategy.md#error-propagation]

## What This Taught You

- **Refactoring for testability vs. rewriting business logic:** the tell is whether the regression test can be written at all. Because `propose_diagnosis` was reused byte-for-byte, Task 4's test could assert "same inputs → identical `cause`/`next_step_action`/`runbook_citation`" with a straight face — if I'd rewritten its internals "while I was in there," any behavior drift would look identical to the regression test passing for the wrong reason (since the test would be checking the new code against itself, not against a fixed prior behavior). The discipline of literally not touching `propose.py` is what made the regression test meaningful instead of decorative.
- **Why a replayable audit log has to be a committed write per node, not an in-memory list:** an in-memory list collected at the end only survives a run that succeeds. The entire point of AC4 ("replayable from the log alone") is for a *failed* run — the one time you actually need to reconstruct what happened. Using `.stream(stream_mode="updates")` instead of `.invoke()` and committing `append_transition` after each node is what makes a run that dies on node 3 of 5 still leave nodes 1-2's transitions on disk, inspectable, instead of losing everything with the in-memory buffer that never got flushed.
- **Why "the graph finished" and "a human decided" can't share one status field:** `PipelineRun.status='completed'` had to mean "the graph ran to completion," full stop — not "and a human has acted on it." The moment you conflate those two, you can't tell the difference between "waiting on a human" and "nothing happened yet," which is exactly the kind of ambiguity that makes an on-call engineer re-page someone or miss a stuck approval. Keeping `approval_status` in ephemeral graph state (not a new DB column) this story, and explicitly deferring the real persisted approval state to Story 3.3, kept that boundary honest instead of fudging a `pending_approval` status value into an enum designed for something else.
