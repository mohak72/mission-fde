# Story 3.4: Evaluation Harness

## Status

Draft

## Story

As a product owner,
I want a repeatable eval scoring retrieval hit-rate and diagnosis usefulness on a fixed 20-incident set,
so that I have a quotable, defendable quality number instead of a vibe.

### Acceptance Criteria

1: A fixed synthetic set of 20 incidents exists, each with a known-correct expected runbook.
2: Running the eval reports retrieval hit-rate (% correct runbook retrieved) across the full set.
3: Running the eval reports an LLM-judge usefulness score per diagnosis, via a judge call distinct from the diagnosis call itself.
4: The eval runs as a single command and produces a persisted report (JSON/markdown) that can be committed or attached to a PR.
5: Target retrieval hit-rate ≥80% (FR8) — if below, this is flagged as a known gap, not hidden.

## Concepts You Need

- **The harness runs the real pipeline, not a copy of it.** Components is explicit: the Eval Harness "runs the fixed 20-incident synthetic set end-to-end through the same `run_pipeline` entry point as production ... not a parallel implementation". If the harness calls `retrieve_runbook` and `propose_diagnosis` itself, it is measuring a pipeline nobody ships. [Source: architecture/components.md#eval-harness]
- **This is the one tier where the LLM is real.** Unit tests mock everything; integration tests mock the Gateway; the eval harness is "this project's functional equivalent of an E2E suite" with real LLM calls. That also means it is the first thing in the project that *cannot produce its headline number without Bedrock credentials* — which this environment has not had since Story 2.1. See Known Gap #1. [Source: architecture/test-strategy-and-standards.md#end-to-end-tests]
- **An LLM judge is a second, separate model call that grades the first one's output.** AC3 requires it to be "distinct from the diagnosis call itself": a different prompt, a different `complete()` invocation, whose only job is to score usefulness. It goes through the Gateway like every other LLM call (NFR1) — the harness never imports `boto3`.
- **AC5 is a reporting requirement, not a pass/fail gate.** If hit-rate is 70%, the correct behaviour of *this* story is a report that says 70%, flags it as below target, and exits successfully. Turning a miss into a build failure is Story 4.2. Tuning retrieval until the number passes is neither — the PRD says low hit-rate "is exactly what Story 3.4's eval harness will surface, not something to pre-solve". [Source: prd/requirements.md#key-risks]
- **There are 11 runbooks and 10 already-used test cases.** `runbooks/` holds 11 files; `tests/fixtures/retrieval_test_cases.py` holds the 10 hand-labeled cases Story 1.3 used and that Story 2.1 then used to *choose* the 0.5 confidence threshold. Those 10 cases are effectively training data for the threshold. The 20 eval incidents must be newly written, or the eval scores the system on the cases it was tuned to. See Known Gap #3.
- **`eval/` exists but is empty** (only `__init__.py`), and no `eval_runs`/`eval_incident_results` tables or models exist yet. [Verified by listing `eval/` and reading `persistence/models.py`]

  - [ ] Create `eval/harness.py` with `run_eval(incident_set, session) -> EvalRun`. [Source: architecture/components.md#eval-harness]
  - [ ] Per incident: insert a synthetic `Alert` via `AlertRepository.insert_if_new` with `external_alert_id = f"eval-{eval_run_id}-{incident_id}"` (unique per eval run, so exact-dedup never skips it) and call `run_pipeline(alert, session)` **directly** — not through the webhook or `ingest_alert`, so Story 3.2's interval-merge cannot collapse deliberately-similar incidents. See Known Gap #4.
  - [ ] Retrieval hit: read the run's `DiagnosisProposal` via `get_by_pipeline_run_id`; `retrieved_runbook_id` = its `runbook_id`, or `None` when no proposal exists (no-match or failed run); `hit = retrieved_runbook_id == expected_runbook_id`. `retrieval_hit_rate = hits / 20`.
  - [ ] Distinguish in the per-incident output *why* there is no proposal: `no_match` (retrieval below threshold — a genuine retrieval miss) vs `pipeline_failed` (`PipelineRun.status == 'failed'` — e.g. a Gateway error). A failed run is not evidence about retrieval quality. See Known Gap #1.
  - [ ] Judge (AC3): `eval/judge.py` with `judge_usefulness(alert, runbook, proposal) -> float`. A separate prompt, a separate `platform_core.gateway.gateway.complete()` call. The prompt gives the judge the alert, the expected runbook's content, and the proposal's cause/action/citation, and requires an exact one-line reply `Score: <1-5>`. Parse strictly: anything else raises (follow `propose.py`'s `_parse_response` / Story 2.1 REL-002 pattern — never default a malformed reply to a number). Normalize to 0–1 (`(score - 1) / 4`) for the `NUMERIC(5,4)` columns.
  - [ ] Incidents with no proposal get `judge_score = 0.0` and **no judge call** (there is nothing to judge; the column is NOT NULL). The aggregate `judge_score` is the mean over all 20, and the report also shows the mean over judged incidents only, labelled as such.

  - [ ] Rate limiting: the run makes up to 40 gateway calls. On `RateLimitExceededError` (Story 3.2) the harness waits and retries that incident a bounded number of times, then records it as `pipeline_failed`/unjudged. It must not abort the whole eval and must not silently skip.
  - [ ] `provider_config` = the same value `run_pipeline` writes to `PipelineRun.llm_provider_config`.
  - [ ] AC5: compute `meets_target = retrieval_hit_rate >= 0.80`. When false, log at `WARNING` (component `eval_harness`) and include an explicit "BELOW TARGET" section in the report listing every missed incident with expected vs retrieved runbook.
  - [ ] Unit tests `tests/unit/eval/` with `run_pipeline` and `complete` mocked: all-hit → 1.0; mixed → correct fraction; no-proposal → `hit=False`, score 0, judge not called; `no_match` vs `pipeline_failed` classified correctly; malformed judge reply raises; score normalization; below-target flagged; rate-limit retry then give-up path.

## Dev Notes

### Previous Story Insights

- `run_pipeline(alert, session) -> PipelineRun` never raises; a failure is `status='failed'` with `node_transitions` showing how far it got. The harness must read status, not rely on exceptions. [Source: apps/incident-copilot/src/incident_copilot/graph/pipeline.py]
- A `DiagnosisProposal` is created only when `diagnosis.matched` is true — so "no proposal" is ambiguous between no-match and failure until you check the run's status (Task 3).
- Story 2.2 noted `retrieve_runbook` runs twice per pipeline run (once in the `retrieve` node, once inside `propose_diagnosis`). Both are deterministic, so the proposal's `runbook_id` is a faithful record of what was retrieved.
- Story 2.3: with no `kind` cluster reachable, every run degrades to `grounded_in_live_state=False`. The eval will therefore measure runbook-only diagnoses in most environments. Record the grounded/ungrounded count in the report so the judge score is interpretable.
- `CONFIDENCE_DISTANCE_THRESHOLD = 0.5` in `retrieval/interface.py` was picked empirically from the 10 existing test cases; correct matches there scored 0.21–0.37. Harder eval incidents may fall above 0.5 and become no-matches. That is a finding to report, not a threshold to move in this story.
- The same QA finding recurred in 2.1, 2.2 and 2.3: tests that feed the code the input it was written for. Here the equivalent is a fake judge that always returns a well-formed score — include malformed-reply and failed-run cases.

### Data Models

- `EvalRun`: `id`, `run_at`, `provider_config`, `retrieval_hit_rate`, `judge_score`, `per_incident_results`. [Source: architecture/data-models.md#evalrun]
- Stored as parent `eval_runs` + child `eval_incident_results` rows (not a JSON array) "because Story 5.1 explicitly needs to compare per-incident results across two `provider_config` values". [Source: architecture/database-schema.md]

## Known Gaps in Architecture Docs

1. **The headline judge number cannot be produced without Bedrock credentials, and no doc says what to do then.** Recommended default: build and fully test the harness with the Gateway mocked; run it for real only when credentials exist; never publish a mocked score as a result. Classify credential/Gateway failures as `pipeline_failed`, separately from retrieval misses, so a credential problem can never masquerade as "0% hit-rate".
2. **The judge's scale and rubric are unspecified.** Recommended default: integer 1–5 with a short written rubric in the prompt (1 = wrong or harmful, 3 = plausible but generic, 5 = correct cause and a specific actionable next step), stored normalized to 0–1.
3. **20 incidents vs. the 10 existing hand-labeled cases.** No doc says whether they may overlap. Recommended default: no overlap — the existing 10 were used to set the confidence threshold.
4. **Data Models says eval is "independent of the live `Alert`/`PipelineRun` tables", but `run_pipeline` requires a persisted `Alert` (FK) and writes `PipelineRun`/`DiagnosisProposal` rows.** These two requirements conflict. Recommended default: honour "same `run_pipeline` entry point" (the stronger, PRD-backed requirement), accept that eval runs write `eval-…`-prefixed rows into the live tables, and document it. A separate schema/database for eval is the clean fix and is out of scope.
5. **Which model judges?** No doc says. Recommended default: configurable, defaulting to the diagnosis model. State in the report that same-model judging is biased toward leniency; a stronger judge model is a one-setting change once credentials exist.
6. **Where do reports live?** AC4 says "can be committed or attached to a PR"; no path is given. Recommended default: `apps/incident-copilot/eval_reports/`, timestamped files plus `latest.json`.
7. **Eval proposals appear in `copilot pending`.** Every eval incident that produces a proposal leaves an undecided proposal in the approval queue. Recommended default: accept for MVP and note it; filtering by the `eval-` alert-id prefix is a small follow-up if it gets annoying.
8. **No committed baseline exists yet.** Story 4.2 needs one. Recommended default: this story produces `latest.json` only; choosing and committing the baseline threshold is 4.2's decision.

## Batch-Draft Assumptions (revalidate before development)

Drafted in a batch before Stories 3.1–3.3 were implemented. This story sits last and leans on all three:

- **Story 3.1 — in-process LRU cache keyed on `(model_id, prompt)`.** Within one `copilot eval` process every prompt is distinct, so the cache should not affect a single run. But if 3.1 ended up with a persistent or cross-process cache, a re-run would replay cached diagnoses *and cached judge scores* — re-check, and bypass the cache for eval if so.
- **Story 3.2 — the limiter rejects with `RateLimitExceededError(GatewayError)`, one token per provider attempt.** Task 3's wait-and-retry is written against that. If 3.2 queues instead, delete the retry logic; if the default bucket is smaller than ~40 calls per run, the eval's runtime is governed by the refill rate — record it.
- **Story 3.2 — interval-merge lives in `ingest_alert`/the webhook, not inside `run_pipeline`.** Task 3 relies on calling `run_pipeline` directly to bypass it. If merge logic moved into `run_pipeline`, similar incidents would be collapsed and the eval would silently score fewer than 20.
- **Story 3.3 — `approval/cli.py` exposes `build_parser()` with subcommands and `[project.scripts] copilot = …` exists.** If not, Task 4 must create the entry point itself.
- **Story 3.3 — its migration is the Alembic head; `DiagnosisProposalRepository` may already have `get_by_pipeline_run_id`.** Check both before writing.
- **Story 3.3 — the `approve` node still returns without blocking.** If 3.3 adopted LangGraph `interrupt()` after all, `run_pipeline` would not complete without a human and the harness could not run unattended.
- **`run_pipeline(alert, session) -> PipelineRun` and "proposal only when matched" are unchanged since Story 2.3.**
