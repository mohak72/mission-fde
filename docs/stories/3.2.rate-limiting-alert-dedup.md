# Story 3.2: Rate Limiting & Alert Dedup

## Status

Draft

## Story

As a platform operator,
I want the gateway to enforce a token-bucket rate limit and alert ingestion to merge near-duplicate alerts by interval,
so that a noisy alert storm doesn't blow the model budget or spam the approval queue.

### Acceptance Criteria

1: The LLM gateway enforces a token-bucket rate limiter (parameters configurable, not hardcoded — see Key Risks); requests over the limit are queued or rejected with a clear error, never silently dropped.
2: Alerts for the same underlying issue arriving within a configurable time window are merged (interval-merge) into a single pipeline run instead of N separate diagnoses.
3: Unit tests cover: limiter allows under limit, blocks over limit, recovers after window; interval-merge merges overlapping alerts and leaves non-overlapping ones separate.

## Concepts You Need

- **This story is two independent features in two packages.** The rate limiter lives in `platform/` (gateway); interval-merge lives in `apps/incident-copilot/` (ingestion). They share a motivation (alert storms) and nothing else. Build and commit them separately.
- **Token bucket in one paragraph:** a bucket holds up to `capacity` tokens and refills continuously at `refill_rate` tokens/second. Each request takes one token; if none is available the request is refused. `capacity` is the burst you tolerate, `refill_rate` is the sustained rate. Refill is computed lazily from elapsed time on each call — there is no background thread.
- **Exact-duplicate dedup already exists and is not what AC2 is about.** `AlertRepository.insert_if_new` does an atomic `INSERT ... ON CONFLICT DO NOTHING` on `external_alert_id` (Story 1.2). AC2 is about *different* `alert_id`s that describe the same problem — e.g. the same pod firing `KubePodCrashLooping` every 30 seconds. The `alerts.dedup_group_id` column and the `idx_alerts_received_at` index were created in Story 1.2 specifically for this story and have never been written to. [Source: architecture/database-schema.md; apps/incident-copilot/src/incident_copilot/persistence/models.py]
- **Nothing in production code calls `run_pipeline` today.** The webhook route ingests the alert and returns; `ingest_alert`'s own docstring says "no second pipeline run is triggered either way, since the Diagnosis Graph does not exist yet (Story 2.2)". Story 2.2 built the graph but deliberately did not wire it to the webhook. So AC2's "merged into a single pipeline run" currently has no pipeline trigger to suppress. See Known Gap #1 — this is the largest open decision in the story.
- **`ingestion/dedup.py` does not exist.** The Source Tree names it; today all ingestion logic is the single `ingest_alert` function in `ingestion/__init__.py`. [Verified by listing `ingestion/`: only `__init__.py`, `auth.py`, `schemas.py`]

## Tasks / Subtasks

- [ ] **Task 1: Token-bucket rate limiter module (AC: 1, 3)**
  - [ ] Create `platform/src/platform_core/gateway/rate_limiter.py` with `TokenBucket(capacity: float, refill_rate: float, clock: Callable[[], float] = time.monotonic)` exposing `try_acquire(tokens: float = 1.0) -> bool`. Lazy refill from elapsed time, capped at `capacity`; thread-safe via `threading.Lock`. [Source: architecture/source-tree.md, architecture/components.md#llm-gateway-platform]
  - [ ] The injectable `clock` is what makes AC3's "recovers after window" testable without `sleep` — do not test this with real time.
  - [ ] Add `llm_rate_limit_capacity` and `llm_rate_limit_refill_per_second` to `platform/src/platform_core/config.py`, plus `llm_rate_limit_enabled: bool = True`. The PRD explicitly flags these values as "still a guess" — they must be settings. [Source: prd/requirements.md#key-risks]
  - [ ] Define `RateLimitExceededError(GatewayError)` in `gateway.py` — a subclass, so every existing `except GatewayError` (including `run_pipeline`'s outer handler) already handles it, and callers who care can distinguish it.
  - [ ] Unit tests `platform/tests/unit/test_rate_limiter.py`, one function each: allows under limit; blocks over limit; recovers after window (advance the fake clock); never exceeds `capacity` after a long idle period; fractional refill accumulates correctly.

- [ ] **Task 2: Enforce the limiter in `complete()` (AC: 1)**
  - [ ] In `gateway.py`, acquire one token **per provider attempt** (i.e. inside the retry loop, immediately before `converse`), after Story 3.1's cache lookup — a cache hit must consume no token.
  - [ ] On refusal raise `RateLimitExceededError` with a message naming the configured limit. Reject, don't queue (see Known Gap #2). Never return an empty/placeholder `LLMResponse` — that would be the "silently dropped" AC1 forbids.
  - [ ] A rate-limit refusal is not retried by the gateway's own backoff loop (retrying into our own limiter just burns the wait).
  - [ ] Update the module docstring in `gateway.py`, which currently says the circuit breaker is deferred until this story — see Known Gap #3 for what to write.
  - [ ] Unit tests in `test_gateway.py`: call under limit succeeds; call over limit raises `RateLimitExceededError` and `converse` is not called; a cache hit while the bucket is empty still succeeds; existing tests still pass (add an autouse fixture resetting the module-level bucket, alongside Story 3.1's cache-clearing fixture).

- [ ] **Task 3: Interval-merge logic (AC: 2, 3)**
  - [ ] Create `apps/incident-copilot/src/incident_copilot/ingestion/dedup.py` with two pure functions (no DB, no clock — trivially unit-testable):
    - `alert_fingerprint(labels: dict[str, str]) -> str` — identity of "the same underlying issue". See Known Gap #4 for the recommended fields.
    - `find_merge_target(fingerprint, received_at, candidates, window_seconds) -> Alert | None` — returns the most recent candidate with the same fingerprint whose `received_at` is within `window_seconds` of the new alert, else `None`.
  - [ ] Add `dedup_merge_window_seconds: int` (recommended default 300) to `apps/incident-copilot/src/incident_copilot/config.py`.
  - [ ] Add to `AlertRepository`: `list_received_since(since: datetime) -> list[Alert]` (uses `idx_alerts_received_at`) and `set_dedup_group(alert_id, group_id) -> None`. No query may be written inline in `ingestion/`. [Source: architecture/coding-standards.md#critical-rules]
  - [ ] Group identity: `dedup_group_id` = the `id` of the first alert in the group (the "leader"). When a follower merges, set the follower's `dedup_group_id`, and also set the leader's own `dedup_group_id` to its own id if still null — so "null" keeps meaning "standalone", per the schema comment.
  - [ ] Chain semantics: compare against the **most recent** alert in the group, not the leader. An alert storm of one alert every 60s for 20 minutes with a 300s window is one group, which is what "interval-merge" means (overlapping intervals collapse) and what AC2's motivation requires.
  - [ ] Unit tests `tests/unit/test_dedup.py`: overlapping alerts merge; non-overlapping stay separate; same window but different fingerprint stay separate; chain of three each within window of the previous merges into one group even though first-to-last exceeds the window; boundary exactly at `window_seconds`.

Recommended: return a small pydantic/dataclass `IngestResult(alert, created, merged_into: UUID | None)` with a `should_run_pipeline` property (`created and merged_into is None`) instead of growing the tuple. Update the webhook route and its five unit tests (which currently mock `ingest_alert` returning a 2-tuple).
  - [ ] Wire the hand-off per Known Gap #1's recommended default: when `should_run_pipeline`, the webhook route schedules `run_pipeline(alert, session)` via FastAPI `BackgroundTasks`, using a **fresh** `SessionLocal()` session opened and closed inside the task (the request-scoped session is closed by the time the task runs).
  - [ ] Webhook response for a merged alert: `{"status": "deduplicated"}` — the REST spec's enum is `[accepted, deduplicated]`; do not add a third value in this story. [Source: architecture/rest-api-spec.md]
  - [ ] Log at `INFO` with component `ingestion`: `alert_merged` with `dedup_group_id` and the fingerprint — never the raw payload.
  - [ ] Integration test `tests/integration/test_alert_interval_merge.py` (real Postgres, Gateway mocked): three alerts with distinct `alert_id`s and the same fingerprint inside the window → exactly one `pipeline_runs` row and all three share a `dedup_group_id`; a fourth with a different fingerprint → a second run. The existing `test_alert_dedup.py` (exact-duplicate path) must still pass unmodified.

## Dev Notes

### Previous Story Insights

- Story 2.1 deferred the gateway circuit breaker "until Story 3.2's token-bucket limiter is built". That sentence is still in `gateway.py`'s docstring. This story builds the limiter; whether it also builds the breaker is Known Gap #3.
- Story 2.2's `run_pipeline(alert, session)` never re-raises: it returns a `PipelineRun` with `status='failed'`. So a `RateLimitExceededError` raised inside the propose node results in a failed, inspectable run — not a crashed background task. No extra handling is needed at the call site. [Source: apps/incident-copilot/src/incident_copilot/graph/pipeline.py]
- Story 2.2 REL-003 is directly relevant to Task 4: a session that has seen a DB error must be rolled back before reuse. The background task must own its own session for the same reason.
- Bedrock credentials are still absent in this environment — the integration test must mock `platform_core.gateway.gateway`'s provider call, as every previous integration test does.

- `alerts.dedup_group_id UUID` — "set by interval-merge (Story 3.2); null if standalone". Already exists, with `idx_alerts_dedup_group`. **No migration is needed.** [Source: architecture/database-schema.md]

- Relationship rule: "One `Alert` → one `PipelineRun`". After this story it becomes one *group* → one run, with the run attached to the leader alert. [Source: architecture/data-models.md#alert]

## Known Gaps in Architecture Docs

1. **No story wires the webhook to `run_pipeline`.** Core Workflows shows `ING->>GRAPH: run_pipeline(alert)`, but no AC in Epics 1–3 says "do this", and the code doesn't. AC2 ("merged into a single pipeline run") is untestable without a trigger. Recommended default: wire it here, minimally, via `BackgroundTasks` (webhook stays fast, returns 202 as the spec says). **This is a scope addition that deserves explicit PO confirmation before development** — the alternative is to stop at "merge decision recorded, `should_run_pipeline` returned" and open a separate story for the hand-off.
2. **AC1 allows "queued or rejected".** Recommended default: reject with `RateLimitExceededError`. Queuing needs an unbounded-or-bounded queue decision, timeouts and a worker — and a queued call that waits past the 30s LLM timeout is a silent drop in disguise.
3. **Error Handling Strategy specifies a per-provider circuit breaker; no AC in any story asks for it.** Recommended default: still out of scope — replace the docstring's "deferred until Story 3.2" with "not scheduled in any story; tracked as a known architecture/PRD gap" and flag it to the PO, rather than building it un-asked or leaving a now-false comment.
4. **"Same underlying issue" is undefined.** Recommended default fingerprint: `alertname` + `namespace` + (`pod`, else `deployment`) + `team`, taken from `payload.labels` (the same labels `classify.py` and `cluster/evidence.py` already read); missing labels contribute an empty string. An alert with no `alertname` is never merged.
5. **Which timestamp defines the window — payload `startsAt` or server `received_at`?** Recommended default: `received_at`. It is server-controlled, it is the indexed column, and the schema comment names it for exactly this purpose.
6. **Concurrent near-duplicates can race.** Two same-fingerprint alerts arriving within milliseconds can each fail to see the other and start two runs. Exact-`alert_id` dedup is atomic; this is not. Recommended default: accept for MVP and document it; a fingerprint advisory lock is the fix if it ever matters.
7. **What unit does a token represent?** Recommended default: one token = one provider call attempt (not LLM tokens). Document this next to the settings — the name invites confusion.
8. **The Source Tree lists `ingestion/pii.py` (FR10) and no story builds it.** Out of scope here; noted because this story is the first to add a sibling file in `ingestion/` and a reader will notice it's missing.
